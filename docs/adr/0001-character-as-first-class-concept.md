# Character を一級概念とし、Class から評価軸を導出する

装備一覧・スカウター入力・転生設定はいずれもキャラクター単位の情報だが、これまでは「キャラ」という概念を持たず、ブラウザに1組だけ存在していた。複数キャラを扱えるようにするにあたり、「名前付き保存セット」を任意個作れるだけの案も検討したが、**Character を一級概念とし、装備一覧・スナップショット・スカウター入力・転生設定をその所有物とする**ことを選んだ。主ステ（`flame-settings.mainStat`）は職で決まる値であり、装備一覧と独立に切り替えられると「STR職の装備一覧にINT設定が残る」という不整合が必ず起きる。所有関係を明示すれば、切り替え＝全部まとめて切り替わる、で不整合が原理的に消える。

同じ理由から、Character は `Class`（職業）を持ち、**主ステ・副ステ・攻撃種は Class から導出して上書きを許さない**（Class設定済みなら各セレクトは `disabled`）。Class が分かっていながら人間に整合性を取らせ続ける理由がなく、上書きに正当な用途も見つからなかったため。Class 未設定の間だけ従来通り手で選べる。副作用として、職の対応表を間違えるとユーザーが手で直せないため、表はリリース前レビューとユニットテストで担保する。

## Consequences

- 主ステが特殊な Xenon・Demon Avenger は、Class から自動的に「転生更新チェック非対応」と判定し、表を出さずに理由を表示する。これまでは静かにそれらしく間違った順位を出していた。強化プラン（★・潜在）は主ステ依存が弱いため従来通り動かす。
- Character が持つのは「そのキャラで読み取った装備の記録」であって「所持品」ではない。装備をキャラ間で移動する機能は持たず、移動先で読み直す。装備を共有プールにして Character が参照する設計も検討したが、記録は時点のスナップであってゲーム内の実体ではないため、実体共有を前提としたモデルとは噛み合わない。
- グリフ辞書（`userbank`）と列表示・プラン表示設定は Character に属さず、ブラウザ全体で共有する。辞書をキャラ別にすると学習が分断されて明確に損。
